# Сервис записи к специалисту

Домашнее задание № 1 по дисциплине «Оптимизация клиент-серверных приложений». Автор: Янковой Артем Александрович, группа БИСТ-24-ПО-3. Первая буква фамилии Я соответствует варианту 3. Личный префикс: `artem_yankovoy`.

## Назначение

Сервис хранит специалистов, услуги, слоты расписания и записи на приём. Авторизованный пользователь выбирает услугу и подходящий свободный слот, бронирует приём без пересечений и может отменить свою запись. Интерфейс содержит список записей с фильтром и постраничным выводом, карточку со связанными данными и сводку загрузки специалистов и доли отмен за период.

## Требования

Проверенные версии: Python 3.12.14, PostgreSQL 16.15, FastAPI 0.118.0, Uvicorn 0.37.0, Psycopg 3.2.10, HTTPX 0.28.1, Pytest 8.4.2. Прямые зависимости закреплены в `requirements.txt`; полный состав библиотек сервиса и тестов закреплён в `requirements.lock.txt`. Для воспроизведения рекомендуется устанавливать полный список. Библиотеки для подготовки отчёта в зависимости сервиса не входят.

Для приведённого ниже запуска PostgreSQL требуется Docker с командой `docker compose`. Если PostgreSQL 16.15 уже доступна локально, шаг запуска контейнера можно пропустить и указать её адрес в `DATABASE_URL`. Исходные измерения выполнены на отдельной переносной PostgreSQL 16.15 под Windows 11; контейнер нужен только как удобный вариант повторного развёртывания.

## Установка и запуск

Распакуйте архив проекта. Первую команду выполните в PowerShell из родительского каталога папки проекта. Остальные команды выполняются из корня проекта, содержащего `compose.yaml`, `seed.py` и `requirements.lock.txt`.

```powershell
cd artem_yankovoy_oksp_hw1
Copy-Item .env.example .env
notepad .env
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.lock.txt
docker compose up -d --wait db
.\.venv\Scripts\python.exe seed.py --schema-only
.\.venv\Scripts\python.exe seed.py --profile small --reset
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

Перед запуском заполните `.env`: задайте собственные `POSTGRES_PASSWORD`, `DEMO_PASSWORD` и `SECRET_KEY`; пароль PostgreSQL в `DATABASE_URL` должен совпадать с `POSTGRES_PASSWORD`. Сохраните `PERSONAL_PREFIX=artem_yankovoy`, `APP_SCHEMA=artem_yankovoy` и `DEMO_USERNAME=artem_yankovoy`. Для команд выше используется HTTP-порт 8000.

`seed.py --schema-only` создаёт таблицы. Флаг `--reset` явно пересоздаёт только выбранную личную схему и её учебные данные; его применяют к собственному учебному стенду. Другие базы и схемы программа не удаляет. Без `--reset` наполнение непустой схемы отклоняется, чтобы не смешивать наборы данных. Наполнение фиксирует генератор `random.Random(42)`, даты и соль учебной учётной записи и печатает количества, контрольные суммы таблиц из PostgreSQL и общую SHA-256.

Для рабочего объёма остановите ручные сценарии и выполните:

```powershell
.\.venv\Scripts\python.exe seed.py --profile work --reset
```

Малый набор содержит 1 пользователя, 10 специалистов, 10 услуг, 500 слотов и 300 записей. Рабочий — 1 пользователя, 200 специалистов, 30 услуг, 200 000 слотов и 50 000 записей. Таблица `users` обеспечивает обязательную авторизацию; четыре предметные сущности соответствуют варианту. В обоих наборах 20% исходных записей отменены.

Проект развёртывания Docker Compose — `artem_yankovoy_hw1`, база — `artem_yankovoy_hw1`, основная схема — `artem_yankovoy`, тестовая схема — `artem_yankovoy_test`.

## Проверка работоспособности

Откройте `http://127.0.0.1:8000`. Войдите под `artem_yankovoy` с паролем, который задали в `DEMO_PASSWORD` до наполнения. Проверьте список записей, фильтр статуса и переходы между страницами; откройте карточку записи. На экране бронирования выберите услугу, найдите свободный слот, создайте запись и отмените её: слот должен снова появиться в списке свободных. На экране сводки задайте период с 01.10.2026 по 01.10.2027 и проверьте загрузку и долю отмен.

В другом окне PowerShell из корня проекта запустите весь набор тестов одной командой:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Тесты проверяют правила совместимости и длительности услуги, пересечения приёмов, освобождение слота после отмены, расчёт сводки и операции контракта: авторизацию, коды ответа, поля, фильтр, пагинацию и ошибки параметров. Тестовые данные создаются автоматически в `artem_yankovoy_test`; рабочая схема `artem_yankovoy` не используется для наполнения тестов. Запуск требует доступной PostgreSQL и заполненного `.env`.

Для отдельного подтверждения воспроизводимости обоих наборов выполните:

```powershell
.\.venv\Scripts\python.exe tools/check_reproducibility.py --reset-generated-schema
```

Проверка дважды наполняет личную тестовую схему каждым профилем, сверяет фактические количества строк и контрольные суммы и сохраняет `results/reproducibility.json`. Выполняйте её отдельно от тестов: оба инструмента используют `artem_yankovoy_test`.

### Повторение исходных измерений

Сервер должен работать одной копией, с одним worker, без режима `--reload`. В `.env` должны быть те же логин и пароль, с которыми создан учебный пользователь. Закройте ручные сценарии, завершите тесты и проверку воспроизводимости, затем выполните:

```powershell
.\.venv\Scripts\python.exe tools/benchmark.py --base-url http://127.0.0.1:8000 --repeats 40 --warmup 5
```

Скрипт последовательно заново создаёт малый и рабочий набор, измеряет все 11 операций API под одной учётной записью и сохраняет `results/measurements.json`, `results/raw-samples.csv`, `results/seed-small.txt` и `results/seed-work.txt`. Прогрев из пяти обращений не включается в 40 измеренных повторов. Медиана p50 при чётном числе повторов — среднее двух центральных значений; p95 — элемент отсортированного ряда с номером `ceil(0.95 × n)`. Максимум также сохраняется. Сравниваются одинаковые параметры, один процесс приложения, последовательные обращения и одинаковая машина.

Общее время ответа измеряется `perf_counter` вокруг полного HTTP-запроса. Сервер отдельно отдаёт время обработки, суммарное время обращений к PostgreSQL и число бизнес-запросов; разность серверного времени и времени БД описывает оставшуюся обработку приложения. Подробные определения заголовков приведены в контракте. Измерение драйвера включает передачу результатов; это не чистое процессорное время СУБД.

Создание и отмена проверяются на заранее свободном контрольном слоте. Перед каждым измерением подготавливается нужное состояние; после него прямой SQL-запрос вне измеренного интервала удаляет только запись, созданную самим скриптом. При 5 прогревах и 40 повторах создаётся 90 временных записей на профиль, итоговый прирост таблицы — 0. Число созданий и оставшихся строк записывается в результаты. Вся серия является исходными замерами ДЗ № 1, а не многопользовательским нагрузочным испытанием.

Фактический стенд отчёта использовал Windows 11 build 26200, Intel Core i5-13450HX, 10 физических ядер / 16 потоков, 15.63 GiB ОЗУ, Python 3.12.14, PostgreSQL 16.15 на `127.0.0.1:55432` и Uvicorn на `127.0.0.1:8000`. Для нового Docker-развёртывания PostgreSQL по умолчанию слушает порт 5432. Различие портов задаётся в `DATABASE_URL`; значения времени с разных машин нельзя считать тем же испытанием.

### Границы первого задания

В реализации ДЗ № 1 нет дополнительных индексов сверх первичных ключей, кеширования ответов, очередей и фоновой обработки. Клиент и сервер используют `Cache-Control: no-store`. Предметные данные хранятся в PostgreSQL; предметных файлов, хранящихся вне БД, нет. Статические файлы интерфейса и исходный код относятся к приложению. Рабочий код остаётся обычной исходной реализацией; оптимизации, нагрузочное испытание и профилирование следующих заданий здесь не выполняются.
